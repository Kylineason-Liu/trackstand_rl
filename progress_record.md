Its `Bu` is the B in `x_dot = A*x + B*u`: **`A = [[0,0,0], [0,0,1], [a2,a4,0]]`, `B = [[1],[0],[a1]]`**. Coefficients are `a1 = m*a*h*v*cos(lambda)/(b*I)`, `a2 = (m*v^2*h - m*a*c*g)*cos(lambda)/(b*I)`, and `a4 = m*g*h/I`, where a is rear-contact-to-COM distance, b wheelbase, c trail, h COM height and I effective roll inertia. - LQR PATH: the registered `balance_node` selects `main_balance.py`. The reviewed configuration uses **200 Hz control**, model/gain refresh every fourth tick (**50 Hz**), and **±10 rad/s** output limits. Normal `main_balance.py` tracks a steering-angle reference; `new_main_balance.py` instead uses a roll reference and is a separate source variant. Rear speed commands are a separate path.
- PID PATH / MAIN DIFFERENCE: `cascaded_balance_node` runs three serial scalar stages: **zero steering-rate error → roll reference → roll-rate reference → Q-axis current → C0**. Default stage limits are **±0.3 rad / ±5 rad/s / ±2 A**, and the declared default period is **0.01 s (100 Hz)**. Each stage uses rectangular error integration, a backward error difference for D, output clipping and integral reset on saturation; comments describing trapezoidal integration/back-calculation are inaccurate. All Ki/Kd defaults are zero. LQR combines the three state errors in one model-designed gain vector; the PID cascade passes each stage's output to the next. Their feedback variables and physical output units also differ: LQR uses steering **angle** and emits **rad/s**, while the intended cascade uses steering **rate** and emits **A**. Its heuristic mapping from absolute LQR/pole gains is not an equivalent LQR realization, and current cannot be inserted directly into the velocity-input B without actuator dynamics.

## 32. MIT CAN command format, control law, and supplied-driver encoding defect (2026-10-04)

- SOURCE / SCOPE: read the local [CAN protocol V3.09b0](<tsinghua_bike_project/assign_2_Hardwares/assign_2_Hardwares/3.RearSteer Servo【GIM3510-8】/CAN Protocol Doc/自定义CAN通信协议_3.09b0.pdf>), especially **pp.20–22** for MIT and **pp.13–14, 23–25** for C0–C3, including the graphical control diagrams. MIT is a different command format/control mode over the same standard CAN transport. No MIT command was sent to hardware and deployment was not switched to MIT.
- FRAME / MODE SELECTION: one standard **11-bit CAN data frame**, **DLC=8**, with ID bit 10 set: **`0x400 | device_address`** or **`0x500 | device_address`**. For motor address 2 these are **0x402 / 0x502**. The eight-byte payload has **no opcode byte**. Receipt immediately switches the driver into MIT mode and executes the command; **CF** disables output/exits MIT, and **B1** is the separate origin-setting command. F0 configures/reads encoding ranges, and F1 reads MIT feedback; neither is the eight-byte motion command.
- FIVE FIELDS / ENCODING: the payload contains **target position p (16 bits, rad), target velocity v (12 bits, rad/s), position gain Kp (12 bits, 0–500), velocity gain Kd (12 bits, 0–5), and feed-forward torque t (12 bits, N·m)**. Position codes **0–65535** map linearly to **−Pos_Max…+Pos_Max**; velocity and torque codes **0–4095** map to their symmetric ranges. Gains instead map **0–4095 to 0–500 / 0–5**. These are unsigned scaled codes, not float32 values or two's-complement signed fields. The documented F0 defaults are **Pos_Max=95.5 rad, Vel_Max=45 rad/s, T_Max=18 N·m**; actual persistent motor settings must be read rather than assumed. F0 stores them as little-endian uint16 values with units **0.1 rad / 0.01 rad/s / 0.01 N·m**, and settings survive power loss. These encoding ranges alone do not establish the motor's mechanical capability or the total PD-plus-feed-forward torque limit.
- EXACT PACKING: MIT motion fields are **high-bit-first**, an exception to the general little-endian C-command format. With p/v/kp/kd/t denoting encoded unsigned values, `{a,b}` concatenating two nibbles, the payload is:

```text
Data[0] = p[15:8]             Data[1] = p[7:0]
Data[2] = v[11:4]             Data[3] = {v[3:0], kp[11:8]}
Data[4] = kp[7:0]             Data[5] = kd[11:4]
Data[6] = {kd[3:0], t[11:8]}  Data[7] = t[7:0]
```

- CHECKED NUMERICAL EXAMPLE: assuming the documented default ranges and truncating the linear encodings, **p=1 rad, v=0 rad/s, Kp=10, Kd=0.2, t=0 N·m** gives raw codes **33110 / 2047 / 81 / 163 / 2047** and illustrative frame **`502#81567FF0510A37FF`**, DLC=8. Quantization means decoding yields approximately **0.998207 rad / −0.010989 rad/s / 9.890110 / 0.199023 / −0.004396 N·m**. This example was checked offline and was not transmitted. Zero physical position/velocity/torque is near the middle of its code range; all-zero payload bytes would not request all-zero physical targets.
- CONTROL LAW / MAIN DIFFERENCE: the p.20 diagram forms **`torque_ref = Kp*(p_des-p_measured) + Kd*(v_des-v_measured) + torque_ff`**, then converts the torque request into a Q-axis current reference. Kp supplies stiffness, Kd supplies velocity-error feedback/damping, and torque_ff adds feed-forward torque; zero Kp/Kd gives intended torque-only control. **C0** sends a single signed current target (**0.001 A/count**), **C1** a single speed target (**0.01 rpm/count**) through speed PI/current control, and **C2/C3** an absolute/relative position target (**16,384 counts/revolution**) through cascaded position PI → speed PI → current control. C0–C3 each use **opcode + little-endian int32, DLC=5**. MIT supplies position, velocity, both gains and torque together on every command and directly combines position/velocity errors into torque; its depicted outer law has no integral term. It is not equivalent to changing C2's opcode or copying B6–B9 PI gains into MIT Kp/Kd. C3's precise repeated-command relative reference remains undocumented as recorded in §27.
- FEEDBACK: a motion-command reply has F1's **seven-byte** format: F1 opcode, **16-bit position**, **12-bit velocity**, **12-bit torque**, and status byte. Status bit 0 indicates MIT mode and bit 1 a system fault. It reports motor state separately from the five desired command fields; no motor acquisition timestamp is specified in this payload. Torque interpretation requires a correctly configured motor torque constant.
- CONFIRMED PYTHON HELPER BUG — **UNFIXED**: [`GIM_Motor_Driver/motor_driver_python/motor.py`](<tsinghua_bike_project/assign_2_Hardwares/assign_2_Hardwares/3.RearSteer Servo【GIM3510-8】/GIM_Motor_Driver/motor_driver_python/motor.py>) lines **913–914** pass Kp and Kd through `_mit_encode`, whose lines **962–967** implement symmetric **−max…+max** scaling. The protocol requires nonnegative gain scaling instead. Requested **Kp=0 / Kd=0** each produce raw code **2047**, decoded by the documented protocol as **Kp=249.938949939 / Kd=2.499389499**, rather than zero. Thus using this helper for intended torque-only control can introduce substantial position/velocity feedback. The numerical mismatch was reproduced offline by extracting and evaluating the actual pure encoder function; no CAN/ROS initialization was needed. Correct gain encoding must map zero to zero and the gain maximum to 4095 separately from symmetric position/velocity/torque encoding. This is a source/protocol defect finding, not a measured firmware response; the helper was not modified in this task.

## 36. Cross-project motor-control compatibility refinements (2026-10-06)

- SCOPE / DEDUPLICATION: compared the current registered `Trackstand-Balance-v0` task, all three deployment motor executables, standalone experiment writers, and `new_balance` entry points. Protocol layouts, experiment numbers, nominal rates, the PID feedback-schema mismatch, and MIT startup/safety behavior are already recorded in §§12 and 27–35; this entry adds compatibility conclusions and more specific source defects, not another copy of those results.
- PHYSICAL ACTION SEMANTICS: RL training/deployment request **steering angle + rear torque**; nominal LQR/pole placement requests **steering angular velocity + separately generated rear speed**; cascaded PID requests **steering current + rear speed**. A common motor or CAN transport does not make these controller interfaces interchangeable. **MIT is a command format/control mode, whereas position/velocity/torque describes the requested behavior**: MIT can implement position-PD or intended torque-only control. Replacing C2 with MIT while retaining the angle target preserves the high-level action meaning, but changes actuator dynamics. Reinterpreting the existing policy's angle/torque outputs as velocity commands is invalid; a position-to-velocity outer-loop adapter adds dynamics requiring validation, while a velocity-output policy needs matching training and retraining.
- SIMULATOR / HARDWARE LOOP DISTINCTION: the active task uses IsaacLab **implicit** actuators: the simulator handles PD, rather than a Python host torque loop or a CAN/MIT implementation. Consequently matching numerical Kp/Kd, command rates, or action scales does not prove equality between solver-side PD, sampled host PD/C0, firmware PI/C2, and firmware PD/MIT. MIT gains are native-motor quantities; arbitrary gearing cannot be ignored when comparing them with joint-space training gains. Sources: [task actions](isaaclab_train/source/trackstand_rl/trackstand_rl/tasks/manager_based/trackstand/trackstand_bike/trackstand_rl_env_cfg.py), [actuators](isaaclab_train/source/trackstand_rl/trackstand_rl/tasks/manager_based/trackstand/bicycle_cfg.py), and [IsaacLab actuator documentation](https://isaac-sim.github.io/IsaacLab/main/source/api/lab/isaaclab.actuators.html).
- RAW ACTIONS / SATURATION: raw policy outputs are **dimensionless**, scaled by **1.57 rad / 6.28 N·m**. The task docstring's assertion that each raw action is in `[-1,1]` is not enforced by its action terms; default RSL-RL `clip_actions=None` is inherited, and the supplied SKRL configuration says `clip_actions: False`. Scaling constants therefore are not guaranteed output bounds. ## 44. Rear-wheel control audit: Isaac Lab, C0, and MIT feed-forward-only (2026-10-07)

- SCOPE / DEDUPLICATION: traced the registered **`Trackstand-Balance-v0`** rear action through the active task/actuator configuration, local Isaac Lab action/implicit-actuator/PhysX submission code, deployment `contracts.py`, `policy_controller.py`, `motor_io.py`, `motor_mit_io.py`, `can_protocol.py` and `mit_protocol.py`; checked the local CAN PDF and existing experiment reports/data. §§23–24 and 32–37 already record the rear direction warning, loop distinction, MIT packet format, exact deployment double-clipping law and architecture recommendation. - DAMPING IS PART OF THE TRAINING INTERFACE: for dimensionless raw rear action **`a_r`**, scaled policy request is **`tau_policy = 6.28*a_r` N·m**, without an enforced raw `[-1,1]` bound. The nominal Isaac rear law is **`tau_policy - 0.05*rear_velocity`**, before solver effects; rear stiffness is zero, but damping is not. - HOW TO MEASURE the bias residual stds: replicate the firmware's stationary calibration window per boot; residual = 0 − estimate; std across 10–30 cold power cycles; sanity ~1e-4..1e-3 rad/s; accel residual from a leveled stand, gravity-component residual per boot. - Measurement protocol detail: keep the bike stationary on its stand through the **same calibration window the firmware actually uses** (example 2–5 s at control rate), or log its already-calibrated output. For each boot, true angular rate is zero, so gyro residual is `0 − bias_estimate`; repeat over 10–30 cold power cycles across hours/days, then use the per-axis residual standard deviation (conservatively, the worst axis) in **rad/s**, not one boot's offset. A result near 0.01–0.1 rad/s suggests calibration is failing; a working calibration should be near max(noise/√N, thermal), roughly 1e-4–1e-3 rad/s. For accel, warm up, level the bike, apply firmware calibration, and compare measured gravity (in g) with the true bike-frame vertical. Use the across-boot standard deviation of each gravity-component residual, conservatively the worst because the sim shares one `accel_res_bias_std`; 0.02 g is about 1.15° of tilt. A fixed mount misalignment is per-unit and should be absorbed by gravity-referenced calibration; include multiple boards only if modeling a fleet. Until measured: if firmware does **not** calibrate, use its uncalibrated bias specification (possibly >0.03 rad/s); if it does, `0.0012/√N rad/s` is a provisional gyro residual estimate. Use a 1–3 h stationary log for Allan-deviation bias instability (`allantools.adev`, curve minimum), check effective **post-filter** white noise, and sweep gyro-bias magnitudes around the measured residual. ## Engine audit for NewBike-Balance-v1 (2026-09-13)
1. solver_position/velocity_iteration_count = 4/2 in `NEW_BIKE_BASE_CFG` articulation properties — ROOT CAUSE of the ~×24.5 sluggish drive: TGS under-delivers the effort-actuated wheel per step. Probe-verified: 16/8 restores the rigid response (wheel slams the 61.6 rad/s limit).

## Training framework facts
- skrl does NOT forward env extras["log"] to TensorBoard (only Reward/Loss/Std/LR) — the motor-speed / DR-ramp diagnostics were converted to terminal prints. rsl_rl DOES forward them — a main reason to prefer it.
- LR schedule was broken: CosineAnnealingLR(T_max=500) annealed to ~0 within ~8k timesteps and stalled 99% of a 1M-step run (reward plateau + rising std). Fixed to KLAdaptiveLR(kl_threshold=0.008).
- rsl_rl setup: scripts/rsl_rl/{train,play,cli_args}.py + agents/rsl_rl_ppo_cfg.py using the current 5.0.1 API (obs_groups + RslRlMLPModelCfg); registered on the balance tasks.
- ~/lmbike_rl = the sibling project that balanced the bike WELL — the reference: rsl_rl, Direct workflow, both motors torque-controlled, tiny [32,32] net, 5-dim obs, 4 s episodes, ~no DR. CycleRL's likely struggles: huge [512,256,128,64] net, 13-dim obs, 30 s episodes, heavy DR, dead LR.
- Action-std diagnostics: healthy = std falls high→low; std RISING while reward falls = the entropy bonus overpowering a weak/regressing signal — lower entropy_coef and/or LR; do NOT just add iterations. Very low std (~0.06) + long episodes = converged.
- train.py override flags: --no_dr (dr_ramp alpha=0), --survival_w/--drive_w/--steer_w (weight 0 = term set to None = fully disabled). They mutate the in-memory cfg BEFORE gym.make (hydra constructs the object; the effective weights ARE recorded in the run's params/env.yaml). BUT survival TYPE (binary vs exp) is a code line-swap, NOT a flag — log the type by hand.
- GPU non-determinism: train.py has cudnn.deterministic=False + TF32 → same cfg+seed gives different policies; sweeps are noise-limited. train_deterministic.py (TF32 off, deterministic algorithms, CUBLAS workspace) makes small changes attributable for a seed — but determinism ≠ generalization (re-check winners on a 2nd --seed).
- rsl_rl checkpoints: model_<iter>.pt every 50 iters, NO best_agent.pt; "latest" = highest iter; verify latest==best via TB. exported/policy.{onnx,pt} can be STALE — re-export from the final model before deploy. play_eval.py prints the eval metrics; --checkpoint <path> loads directly. play_with_metrics.py is skrl-only.
- The reward manager computes `value * weight * dt` — a penalty FUNC that already returns negative values needs a POSITIVE weight (a negative weight flips it into a reward; confirmed in TB as the iter2 servo slamming). Decide per-project whether penalties are negative-funcs (weights positive) or positive-funcs (weights negative); verify the per-term TB sign after one run.

## Reward design lessons
- Don't compare mean reward across reward-weight changes (changing a weight changes the reward SCALE mechanically). Episode length is scale-invariant and honest — but SATURATES near the timeout; beyond that use non-saturating behavior metrics (kick recovery, DR survival, roll/steer RMS).
- Only the RATIOS among reward terms define the objective (PPO normalizes advantages; overall scale is ~irrelevant — only the value loss is scale-sensitive).
- Positive vs negative: keep net per-step reward >= 0 (an unavoidable negative per-step term can make the agent prefer to terminate — "suicidal agent"). Use a reward (not a penalty) when the ideal value isn't achievable while doing the task (steering MUST move to balance).
- steer_reward specifically: steering is the PRIMARY balancing actuator — rewarding still steering directly opposes balancing; its balance-optimal weight ≈ 0 (its only upside is smoother steering for motor wear / sim-to-real).
- Calming an actuator is free ONLY if it isn't the task's control authority: high drive_reward helped (velocity-controlled drive wheel = pure disturbance); high steer_reward hurts (steering IS the control). Corollaries: don't tune drive and steer on a shared ratio (their roles are asymmetric); anchor every steer sub-sweep at steer=0; gate high-steer runs on data.
- A one-time termination penalty is minor (falling already forfeits the entire discounted future survival stream at γ=0.99; the explicit −10 mainly helps early training).
- Gradient placement: exp(−k·roll) concentrates the gradient at the target (precision near upright, weak in the fall zone); arctan at a midpoint concentrates it where the bike is actually falling; BINARY step reward has no per-step gradient (learns only via alive-time + termination). Self-normalize arctan by its vertical value so the weight stays the peak reward. Very small sharpness makes arctan ~linear.
- Weight tuning method: coordinate descent misses interactions; single runs are stochastic — use 2–3 seeds and COARSE sweeps (4/12/24, not 11/12/13/14 below the noise floor); tune on the TARGET task distribution (DR on).
- Shaping family: band (plateau+tail) beat quadratic & Gaussian on eval ep_len and roll RMS (bands give a flat "good enough" basin with a clear escape gradient). DR terms change WHICH optimum is reachable — re-verify winners under their trained DR regime.
- Don't trust "both configs do well" when they differ on multiple axes (fully confounded) — hold the confounding axes constant and vary ONE at a time.

- Early verdict: the AUTHORED full-DR ranges (mass 0.5–1.5×, tire friction 0.5–1.2, IMU bias/latency) are beyond what the plant learns: from-scratch DR sweep (d=2/5/10/12/20, 15k) — all solved the easy regime by ~iter 500 then the ramp collapsed every one (final d5/d12 tie ~365, fallen 0.86–0.92; d20 dead). - REFINED (2026-09-06, per-term ablation from a common baseline, true in-distribution evals): friction 0.5–1.2 / mass 0.5–1.5× = ACCELERATORS (perfect 1500/100% by ~15k, ~4× faster than no-DR — dynamics diversity prunes degenerate strategies); roll-pose/roll-vel mildly useful; IMU slows but rescuable with 4× budget (1130/72.6% at 60k vs 1500/100% noise-off); COM lateral (y) is the poison, x/z safe-to-beneficial.

- IMU-term decomposition: gyro bias = the KILLER (constant roll-RATE offset → corrective drive → wheel_net runaway, 95.9% wheel_net deaths, 0.6% timeouts); tilt bias nearly free (1500/100%); latency alone ~62–65% timeouts.

## IMU error model summary
- Deterministic/calibratable: turn-on bias, scale-factor (±0.5% typ), nonlinearity, misalignment, g-sensitivity, vibration rectification (NOT boot-calibratable), quantization. Stochastic: white noise (ARW/VRW — datasheet 0.07°/s RMS gyro = 0.0012 rad/s, 0.001 g RMS accel; these fix the WHITE-NOISE term, NOT the bias — noise ≠ bias: white AC per sample vs DC per-episode constant), bias instability (1/f wander — measurable via stationary 1–3 h log → allantools.adev → curve minimum), rate/accel random walk. Environmental: thermal drift + power-on transient.
- Sim mapping: gyro_res_bias_std = #1 residual (original 0.03 rad/s = 1.72°/s uncalibrated scale, ~300–1000× above the post-cal residual ≈ noise/√N ≈ 1e-4..1e-5 rad/s); gaussian obs noise = #8 (was DEAD in every pre-2026-09-08 run; the old authored 0.01 uniform was 8–10× too big); #9 negligible at 30 s episodes.
- Implemented 2026-09-08: enable_corruption=True + per-channel tuple-std noise (0.001 gravity / 0.0012 angvel / 0 elsewhere); event renamed to reset_imu_turnon_residuals; obs 13→9 dims (later restored to 13 by the 2×2 verdict). Remaining: measure per-boot residual spread; Allan bench test; gyro-bias magnitude sweep to find the tolerance cliff below 0.03.

## Friction combine rules (2026-09-13/16)
- PhysX combines two materials' friction with the default AVERAGE mode; MuJoCo combines pair friction with MAX (verified empirically: 1.0×0.5→1.0). To make MuJoCo land on a target effective pair, put that value on BOTH geoms.
- MuJoCo's friction triple is (sliding, torsional, rolling) — NOT longitudinal/lateral; PhysX has only sliding (static/dynamic). A faithful MuJoCo port sets torsional/rolling to 0.
- NewBike-Balance-v1 reference: robot 0.5 × pinned ground 1.0 → effective pair 0.75 (tire DR 0.5–1.2 per reset). Trackstand pair: explicit 0.5/0.5/0 on the collision overs × pinned 1.0 ground → 0.75 both engines.

## Collision pipeline (2026-09-13/15)
- Isaac Lab runtime colliders come from the USD's collision meshes, cooked per the physics:approximation token (URDF converter authors "convexHull"). Tokens: boundingCube | boundingSphere | convexDecomposition | convexHull | none | meshSimplification | sdf. PhysX has NO ellipsoid/cylinder primitive collider.
- MuJoCo: the <geom> in the XML IS the runtime collider; mesh geoms with contype 0 are visual-only.
- URDF-import layout: each link = two instanced Xforms (<link> visual, <link>_1 collision with purpose="guide"); the collision mesh child is inside an instanced prototype — invisible to plain stage traversal; the guide-purposed colliders are what "collision from visuals" deletes.
- THE VERIFIED PHYSX SDF RECIPE: approximation="sdf" ALONE is rejected (falls back to convexHull); the SDF branch is gated on applying PhysxSDFMeshCollisionAPI (token + API together). The API carries sdfResolution 256, sdfSubgridResolution 6, sdfNarrowBandThickness 0.01, sdfMargin 0.01 (spacing ≈ AABB/256 ≈ 0.55 mm on a wheel).
- Patch mechanics: USD forbids authoring through instance proxies → edit the payload-layer spec directly via Sdf (apply_wheel_sdf.py).
- Defaults: an un-marked USD collision mesh is cooked as convexHull; none = raw trimesh.
