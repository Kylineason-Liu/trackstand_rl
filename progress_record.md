## Training framework facts
- skrl does NOT forward env extras["log"] to TensorBoard (only Reward/Loss/Std/LR) — the motor-speed / DR-ramp diagnostics were converted to terminal prints. rsl_rl DOES forward them — a main reason to prefer it.
- LR schedule was broken: CosineAnnealingLR(T_max=500) annealed to ~0 within ~8k timesteps and stalled 99% of a 1M-step run (reward plateau + rising std). Fixed to KLAdaptiveLR(kl_threshold=0.008).
- rsl_rl setup: scripts/rsl_rl/{train,play,cli_args}.py + agents/rsl_rl_ppo_cfg.py using the current 5.0.1 API (obs_groups + RslRlMLPModelCfg); registered on the balance tasks.
- ~/lmbike_rl = the sibling project that balanced the bike WELL — the reference: rsl_rl, Direct workflow, both motors torque-controlled, tiny [32,32] net, 5-dim obs, 4 s episodes, ~no DR. CycleRL's likely struggles: huge [512,256,128,64] net, 13-dim obs, 30 s episodes, heavy DR, dead LR.
- Action-std diagnostics: healthy = std falls high→low; std RISING while reward falls = the entropy bonus overpowering a weak/regressing signal — lower entropy_coef and/or LR; do NOT just add iterations. Very low std (~0.06) + long episodes = converged.
- train.py override flags: --no_dr (dr_ramp alpha=0), --survival_w/--drive_w/--steer_w (weight 0 = term set to None = fully disabled). They mutate the in-memory cfg BEFORE gym.make (hydra constructs the object; the effective weights ARE recorded in the run's params/env.yaml). BUT survival TYPE (binary vs exp) is a code line-swap, NOT a flag — log the type by hand.
- GPU non-determinism: train.py has cudnn.deterministic=False + TF32 → same cfg+seed gives different policies; sweeps are noise-limited. train_deterministic.py (TF32 off, deterministic algorithms, CUBLAS workspace) makes small changes attributable for a seed — but determinism ≠ generalization (re-check winners on a 2nd --seed).
- rsl_rl checkpoints: model_<iter>.pt every 50 iters, NO best_agent.pt; "latest" = highest iter; verify latest==best via TB. exported/policy.{onnx,pt} can be STALE — re-export from the final model before deploy. play_eval.py prints the eval metrics; --checkpoint <path> loads directly. play_with_metrics.py is skrl-only.
- The reward manager computes `value * weight * dt` — a penalty FUNC that already returns negative values needs a POSITIVE weight (a negative weight flips it into a reward; confirmed in TB as the iter2 servo slamming). Decide per-project whether penalties are negative-funcs (weights positive) or positive-funcs (weights negative); verify the per-term TB sign after one run.

## Reward design lessons
- Don't compare mean reward across reward-weight changes (changing a weight changes the reward SCALE mechanically). Episode length is scale-invariant and honest — but SATURATES near the timeout; beyond that use non-saturating behavior metrics (kick recovery, DR survival, roll/steer RMS).
- Only the RATIOS among reward terms define the objective (PPO normalizes advantages; overall scale is ~irrelevant — only the value loss is scale-sensitive).
- Positive vs negative: keep net per-step reward >= 0 (an unavoidable negative per-step term can make the agent prefer to terminate — "suicidal agent"). Use a reward (not a penalty) when the ideal value isn't achievable while doing the task (steering MUST move to balance).
- steer_reward specifically: steering is the PRIMARY balancing actuator — rewarding still steering directly opposes balancing; its balance-optimal weight ≈ 0 (its only upside is smoother steering for motor wear / sim-to-real).
- Calming an actuator is free ONLY if it isn't the task's control authority: high drive_reward helped (velocity-controlled drive wheel = pure disturbance); high steer_reward hurts (steering IS the control). Corollaries: don't tune drive and steer on a shared ratio (their roles are asymmetric); anchor every steer sub-sweep at steer=0; gate high-steer runs on data.
- A one-time termination penalty is minor (falling already forfeits the entire discounted future survival stream at γ=0.99; the explicit −10 mainly helps early training).
- Gradient placement: exp(−k·roll) concentrates the gradient at the target (precision near upright, weak in the fall zone); arctan at a midpoint concentrates it where the bike is actually falling; BINARY step reward has no per-step gradient (learns only via alive-time + termination). Self-normalize arctan by its vertical value so the weight stays the peak reward. Very small sharpness makes arctan ~linear.
- Weight tuning method: coordinate descent misses interactions; single runs are stochastic — use 2–3 seeds and COARSE sweeps (4/12/24, not 11/12/13/14 below the noise floor); tune on the TARGET task distribution (DR on).
- Shaping family: band (plateau+tail) beat quadratic & Gaussian on eval ep_len and roll RMS (bands give a flat "good enough" basin with a clear escape gradient). DR terms change WHICH optimum is reachable — re-verify winners under their trained DR regime.
- Don't trust "both configs do well" when they differ on multiple axes (fully confounded) — hold the confounding axes constant and vary ONE at a time.

## Friction combine rules (2026-09-13/16)
- PhysX combines two materials' friction with the default AVERAGE mode; MuJoCo combines pair friction with MAX (verified empirically: 1.0×0.5→1.0). To make MuJoCo land on a target effective pair, put that value on BOTH geoms.
- MuJoCo's friction triple is (sliding, torsional, rolling) — NOT longitudinal/lateral; PhysX has only sliding (static/dynamic). A faithful MuJoCo port sets torsional/rolling to 0.
- NewBike-Balance-v1 reference: robot 0.5 × pinned ground 1.0 → effective pair 0.75 (tire DR 0.5–1.2 per reset). Trackstand pair: explicit 0.5/0.5/0 on the collision overs × pinned 1.0 ground → 0.75 both engines.

## Collision pipeline (2026-09-13/15)
- Isaac Lab runtime colliders come from the USD's collision meshes, cooked per the physics:approximation token (URDF converter authors "convexHull"). Tokens: boundingCube | boundingSphere | convexDecomposition | convexHull | none | meshSimplification | sdf. PhysX has NO ellipsoid/cylinder primitive collider.
