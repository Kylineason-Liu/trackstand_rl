1. Why Is Low‑Speed Balancing So Hard?

🏍️ The Physics

When a bicycle turns, two moments act on the roll axis:

  • Centrifugal moment Tvx ∝ vx² · δ — vanishes as speed drops
  • Front-fork additional moment Tc ∝ c · δ — depends on trail (拖曳距 c)

At low speed, the centrifugal moment is too weak to counteract gravity.

❌ The Current Bottleneck

new_main_balance.py clamps min_scheduling_speed = 1.0 m/s.

Below that, the 3-state linear model becomes degenerate — A(v), Bu(v) produce gains that don't work well.

Result: The real bike can't balance below ~1.0–1.3 m/s with the current controller.

The thesis asks: can we push the balance speed down to ~0.58 m/s (2 km/h) — a walking pace?

2. Physical Insight — Trail (拖曳距 c) Is Everything

Normal Bike: c ≈ +0.08 m (正拖曳距)

Front wheel contact point is behind the steering axis intersection.

Tc opposes Tvx → net steering moment is weak at low speed.

Cannot balance below ~1.3 m/s

Modified Bike: c = −0.09 m (负拖曳距)

Front wheel contact point is ahead of the steering axis intersection.

Tc reinforces Tvx → steering moment is amplified.

Balances down to 0.58 m/s ✓

How to modify: Keep the steering axis fixed; move the front wheel forward. Since b + c = constant (wheelbase + trail), increasing |c| in the negative direction also increases the wheelbase b — this reduces turning agility but improves low-speed stability.

3. Simplified SISO Model & the Key Parameter KF

From 3-state to 1-input 1-output

The thesis simplifies the full dynamics by:

  1. Ignoring forward dynamics — speed vx is treated as a constant parameter
  2. Ignoring steering dynamics — motor position control is fast enough that δ ≈ δcmd
  3. Small-angle linearization — sinφ≈φ, cosφ≈1, drop product terms

This gives a SISO system: δ → φ (steer angle → roll angle)

G(s) = φ(s) / δ(s) = −ahsλvx·s + (acg − hvx²)·sλ / (bh²·s² − gh·b)

The Feedforward Coefficient KF

At steady-state equilibrium (φ̇ = 0, δ̇ = 0), the ratio of steer angle to roll angle is:

K0 = δss / φss = gh·b / (h·vx²·sλ − a·c·g·sλ)

KF ≈ K0 determines everything

Smaller |KF| → easier balance, better disturbance rejection
Larger |KF| → harder, eventually impossible

Critical speed vxc = √(acg/h) ≈ 0.7 m/s for c=0.08 m. When vx → vxc from above, KF → +∞ (division by zero), then flips sign.

KF — Feedforward

Provides the "bulk" of the command. Theoretically computed from the linearized model. In practice ~20% error from model mismatch; the integrator cleans up the residual.

KP, KD — PD Feedback

Stabilizes the open-loop unstable dynamics. KD suppresses overshoot. Stability requires |KP + KF| > 0 and appropriate signs.

KI — Integral

Eliminates residual steady-state error from model mismatch. Feedforward-first, integral-supplementary — avoids slow integrator dynamics dominating.

Gain Trend vs. Speed

As speed increases:

  • |KF| decreases — centrifugal moment grows, less steer angle needed per roll angle
  • |KP| decreases — same reason; the system becomes "stiffer" aerodynamically
  • |KD| decreases — less damping needed when centrifugal effect is stronger
  • |KI| decreases — less residual error to clean up

All four gains' absolute values monotonically decrease with speed — the faster you go, the easier balancing becomes.

6. new_main_balance.py — 3-State LQR / Pole‑Placement

State: x = [δ, φ, φ̇]T    Input: u = δ̇ (steering angular velocity)
Model: ẋ = A(v)·x + Bu(v)·u    Law: u = ueq + K·(xeq − x)

🔧 Continuous Gain Scheduling

Every tick (100 Hz): recompute A(v), Bu(v) from the nominal bike model, then update the LQR/pole gain K. min_scheduling_speed = 1.0 m/s clamps the model.

⚖️ Equilibrium + State Ref

solve_equilibrium(steer_ref) → x_eq = [δ_eq, φ_eq, 0], then step_with_state_reference(x_eq, state). The control law tracks toward the equilibrium state.

⚡ Output = Steer Velocity

The controller directly outputs steering angular velocity (rad/s), sent as C1 speed commands to the GIM motor. No inner position loop — the motor runs in speed mode.

LQR Cost Structure

Q = diag([4, 100, 2])   R = [10]

State costs: δ=4 (moderate steer penalty), φ=100 (heavy roll penalty — safety), φ̇=2 (light damping). Control cost R=10 penalizes aggressive steering velocity.

Pole placement default: wc = −14.3 (all 3 closed-loop poles at −14.3). This is significantly more aggressive than the thesis PID — the thesis PID's dominant pole is typically much slower (the system is a physical bike, not a simulation).

8. Two Different Control Philosophies

📘 Thesis: Physics-Aware Simplicity

  • Change the plant first, then control it simply. The negative trail modification makes the bike inherently easier to balance at low speed.
  • "The feedforward coefficient KF is everything" — if |KF| is small, even a simple PD will work.
  • PID+FF is well-understood, easy to tune field-by-field, and naturally handles the "counter-steer first" transient.
  • Piecewise gain tables require experimental tuning per speed band — labor-intensive but robust to model errors.
  • Trade-off: negative trail reduces low-speed turning agility (larger turning radius).

💻 Ours: Model-Based Optimality

  • Trust the model, compute the optimal gains. LQR/pole-placement gives mathematically optimal feedback for the linearized model.
  • Continuous gain scheduling is elegant — no discretization artifacts.
  • But: the model is the weak link. When A(v), Bu(v) don't match reality (wrong params, unmodeled dynamics), optimal gains for the wrong model ≠ optimal for the real bike.
  • min_scheduling_speed = 1.0 m/s is a hack — the model degenerates below that speed, so we clamp it.
  • No physical trail modification considered.

Core insight: "All models are wrong, but some are useful."

The thesis acknowledges model error explicitly and uses feedforward + integrator to compensate. Our approach depends on the model being accurate — when the model fails (low speed), there's no fallback except clamping.

🌍 Terrain Handling (c=−0.09m)

  • Speed bumps: stable at ≥0.85 m/s (limited by motor torque, not balance)
  • Grass (continuous bumps): stable at ≥0.9 m/s — roll oscillates but stays tracked
  • Downhill (−4.5°): speed rises from 0.83→1.36 m/s, gains auto-switch, braking activates
  • Uphill (+7.5°): speed drops from 1.67→0.9 m/s, gains auto-switch down
  • Active speed change: 0.78→2.25 m/s ramp — balance maintained throughout

10. How to Improve Our Bike: A Hybrid Approach

🔧 Step 1: Measure Our Trail

Our current bike has c=0.01m (nearly zero!). The thesis shows c > 0 is fundamentally limiting for low-speed balance. Consider:

  • Measure actual trail on our physical bike
  • If possible, design an adjustable front fork to experiment with negative trail
  • Even c ≈ −0.05 m would substantially reduce KF at low speeds

🧠 Step 2: Add Feedforward

The biggest missing piece vs. the thesis. Add to the control law:

u = ueq + K·(xeq−x) + KF·φd

This provides immediate, model-based feedforward that doesn't wait for error to build up. Compute KF from our bike params at each speed.

📊 Step 3: Validate & Compare

  • Simulation first: Add the simplified SISO model + PID+FF to our MuJoCo sim. Compare with LQR at vx ∈ [0.5, 1.5] m/s.
  • If PID+FF wins at low speed: implement hybrid mode — LQR for vx > 1.5 m/s (optimal at speed), PID+FF for vx < 1.5 m/s.
  • Hardware: If trail can't be modified, at minimum add the feedforward term to the existing LQR controller.

Concrete Changes to new_main_balance.py

  1. Add K_F computation: from bike params + current speed, compute the theoretical feedforward gain and add K_F * roll_target to the steer rate command.
  2. Add K_I (integral): accumulate roll error and add to command. This compensates for systematic model mismatch.
  3. Reduce min_scheduling_speed: from 1.0 → 0.5 m/s. The model may be less accurate there, but feedforward + integrator can compensate.
  4. Consider PD on roll directly: as an alternative method: pid_ff alongside pole and lqr. This would mirror the thesis controller structure exactly.
  5. Steer position inner loop: wrap the steer motor in a P position controller (thesis style) to convert steer angle commands to motor speeds, rather than direct speed output.
