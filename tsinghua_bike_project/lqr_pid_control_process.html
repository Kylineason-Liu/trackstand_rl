These are different actuator interfaces. The three-state model defines its input as steering angular velocity; PID’s final current needs motor dynamics before it becomes that velocity.

The largest algorithmic difference: one coupled decision versus a cascade.

LQR uses the bike model to choose a joint gain vector, then adds all three state-error contributions at once. Cascaded PID closes three scalar error stages in sequence; one stage’s output becomes the next stage’s reference. In this repository, their final commands also differ: LQR → steering speed; PID → steering current.

The main comparison follows source/new_balance/new_balance/main_balance.py and cascaded_main_balance.py. The older bike_balance package, backup LQR + PD architecture, and teaching notebook’s LQR + PI architecture are distinguished below. This page describes source logic, including defects; it does not establish that these nodes run successfully on hardware.

The bicycle plant and its state

The imported nominal_bike_control.LinearBicycleModel is a continuous-time, speed-scheduled, three-state roll–steer approximation. Its matrix named Bu is the B in x′ = Ax + Bu.

Steering angle and steering rate affect roll acceleration. The positive gravity term a4φ drives the upright bike away from equilibrium.

a1 = m a h v cos(λ) / (b I)
a2 = (m v² h − m a c g) cos(λ) / (b I)

a1 has units s⁻¹; a2 and a4 have units s⁻². Cm = I₃: all three states are measured directly. There is no state or disturbance observer in this controller.

LQR: a model-derived, full-state speed command

balance_node → main_balance:main The normal launch selects this executable. method="lqr" chooses continuous-time LQR; pole placement is another gain-design method for the same state-feedback law.

All three contributions are summed.

Design and rescheduling

  1. Build A(v) and B(v)

    Use the physical parameters and the speed schedule. Every fourth control tick, update the model and pass bike.sys into update_system_and_gain.

  2. Choose the quadratic costs

    Q weights steering, roll and roll rate; R weights steering-speed effort. The current YAML sets Q = diag(1.296177, 840.858646, 4.692319) and R = [1.182898].

    J = ∫₀∞ (eᵀQe + ΔuᵀRΔu) dt
    e = x − xeq,   Δu = u − ueq

  3. Solve the continuous Riccati equation

    AᵀP + PA − PBR⁻¹BᵀP + Q = 0
    K = R⁻¹BᵀP

    The code calls solve_continuous_are, then solves R K = B.T @ P. The ideal unsaturated closed-loop matrix is A − BK.

[2] controller.py:185–205 · [3] main_balance.py:1208–1218

Every control tick: state → output

  1. Read the three measured states

    δ from /steer_info[0]; φ and φ̇ from /roll_info[0] and [3]. No prediction, integral state or numerical error differentiation is used in the LQR law.

  2. Solve a physically consistent equilibrium

    In the launched main_balance.py, track_roll=False, so Co = [1, 0, 0] and r is the steering-angle reference. It is RC data[1] in RC mode, or zero in fixed mode.

    Axeq + Bueq = 0
    Coxeq = r
    xeq = [r, −(a2/a4)r, 0]ᵀ
    ueq = 0

  3. Sum weighted errors, then clamp

    u* = kδ(δeq − δ)
      + kφ(φeq − φ)
      + kφ̇(0 − φ̇)
    u = clip(u*, −10, +10) rad/s

    The controller already clips to its limits; the ROS node clips again. Thus its sat_outer comparison uses an already-clipped value and can miss actual saturation.

  4. Pass the command through the output gates

    Send C1 steering speed only when armed; send the calculated speed only if the RC servo flag is 1. Otherwise the armed steering path sends C1 = 0. Apply steer_direction_invert (true in YAML) before encoding. dry_run skips CAN transmission.

Exactly what goes onto CAN

s = −1 if inverted, otherwise +1
rawC1 = round(s u × 60/(2π) × 100)
payload = [0xC1] + int32LE(rawC1)

The steering host CAN ID is 0x101; motor feedback is 0x001. C1’s integer unit is 0.01 rpm. The built-in motor speed controller supplies the current/torque needed to follow this speed. Its internal gains and actual tracking performance are not determined by this LQR code.

[3] main_balance.py:891–912, 1248–1259 · [12] protocol, C1

Timing, rear drive and interruptions

Control, fault checks and C1 output: 200 Hz (5 ms). Model + gain update: 50 Hz, every four ticks. Gain computation uses continuous A and B, not a discrete Riccati equation.

The rear motor receives its own C1 on 0x102: RC throttle RPM, or a fixed-speed ramp converted through the 0.07 m wheel radius. It influences the forward speed used by the balance model.

Missing/stale roll or steer topics (0.15 s) disarm; excessive roll (>30°) stops both motors. Steering beyond 30° in the supplied YAML latches CF on the steer motor; the rear may continue following its reference while that fault holds. Recovery requires centering within 0.3°. These are source thresholds, not guarantees of physical balance.

The alternative new_main_balance.py changes what the RC reference means

It uses the same A, B and K computation, but track_roll=True sets Co = [0, 1, 0]. Its callback stores half of RC data[1]; the feedback tick negates that stored value. Therefore φref = −0.5 × RC.data[1], and xeq = [−(a4/a2)φref, φref, 0]ᵀ. Its default speed clamp is 15 rad/s, while the supplied YAML says 10. setup.py does not register this file as balance_node.

Current wiring does not supply the measured steering rate

cascaded_main_balance._steer_cb reads msg.data[1] into _steer_rate. The current steer_publisher publishes [steer_angle, time.time()]. A timestamp is therefore treated as rad/s. The diagram above describes the intended inputs to the written PID algorithm; the actual pair of files violates that contract.

How each PID step is actually computed

The same PID.step(error, dt) is called once for each stage. Let S be stored integral and eprev the prior error.

S ← S + e × Δt
P = Kpe
I = KiS
D = Kd(e − eprev) / Δt
z* = P + I + D
z = clip(z*, zmin, zmax)
if clamped: S ← 0
eprev ← e

Code guards the integral at Δt > 0 and the derivative at Δt > 10⁻⁹. It uses rectangular integration, an unfiltered backward error difference, and integral reset on saturation. Despite comments claiming trapezoidal integration and back-calculation, those algorithms are not implemented.

Reset clears S and eprev to zero. If Kd is enabled, the first nonzero error after reset creates a derivative step. All six Ki/Kd defaults are zero, so the default cascade performs only proportional calculations.

[5] cascaded_main_balance.py:156–228, 285–302

Initialization, then a complete tick

  1. Use the nominal model to obtain an initial K

    The constructor uses the model’s default 2 m/s. PID defaults: mass 2.237 kg, a = 0.135 m, trail = 0.010 m. It defaults to repeated pole placement at −14.3, with optional LQR Q = diag(4, 100, 2), R = [10].

  2. Convert K to three heuristic proportional gains

    Kp,i = |kφ̇| × Kt
    Kp,m = clip(|kφ|/max(|kφ̇|, .01), .5, 50)
    Kp,o = clip(|kδ|/max(|kφ|, .01), .05, 10)

    Nonnegative explicit gain overrides replace these defaults. Kt defaults to 1 Nm/A; the node does not query B0 to establish it.

  3. Read measurements and run outer → middle → inner

    After freshness checks, the start delay and the armed condition, compute the three errors and pass each clamped result to the next stage. Δt defaults to 0.01 s, so the timer is 100 Hz, despite the “50 Hz” docstring.

  4. Apply fault decisions, encode current, send C0

    Apply the steering direction sign to Iq; send on 0x101. Rear drive remains a separate C1 speed path on 0x102. Arm and steering-fault transitions reset the PID histories.

The physical plant input is different here

uPID,physical = Iq   [A]
rawC0 = round(s Iq × 1000)
payload = [0xC0] + int32LE(rawC0)
τsteer = Kt,actual × s Iq   [Nm]

The current command produces torque, which accelerates the steering mechanism. Actual δ̇ depends on motor/steer inertia, friction, load and firmware behavior. The repository supplies no current-input A and B for this cascade. Iq cannot be substituted into the velocity-input B above.

[5] cascaded_main_balance.py:589–605, 867–873 · [12] protocol, C0

This mapping does not reproduce LQR

With only P terms and no clamps, write the three proportional gains as go, gm, gi. Substituting the cascade gives:

Iq = −gigmgo δ̇
      −gigm φ −gi φ̇

LQR instead feeds back δ, φ and φ̇ and outputs rad/s. This cascade feeds back steering rate, discards the signs of K during gain mapping, and outputs A. Neither the input units nor the first feedback variable match. The gain mapping is a heuristic, not an algebraic conversion of the LQR controller.

Other concrete PID-path limitations in the source
The optional gain scheduler is disconnected from the updated model.

_tick_full updates self._bike.sys, but _update_cascaded_pids calls only self._ctrl.update_gain(wc=...). The controller copies A and B at construction, so pole-based updates remain at the constructor’s 2 m/s. In LQR mode that call replaces Q/R options with wc and raises ValueError: 'Qc' and 'Rc' are required for lqr. Scheduling defaults to false.

No direct steering-angle reference or centering feedback in the normal PID law.

δ is read for the soft limit, not fed into the three PID errors. Its outer target is zero steering rate, not zero steering angle. The RC callback consumes only drive RPM, unlike the LQR path’s steering reference.

The same params.yaml does not configure the PID executable automatically.

The YAML controller section is new_balance_node; this executable constructs cascaded_balance_node. It declares control_dt, not control_hz. References to config/cascaded_params.yaml appear in comments, but that file is absent in this checkout. The two controllers’ default geometries and gains differ.

Fault behavior also differs.

PID uses a fixed 0.5 s roll/steer topic timeout. Steering fault recovery uses 5% of its 30° limit (1.5°). In full mode its rear drive may continue during a steering fault. There is no declared dry_run path or RC servo-up output gate in this PID node.

“D” in PID is not the same operation as LQR’s roll-rate term.

LQR multiplies the already measured φ̇ by a feedback gain. PID’s D term differentiates a stage’s error over successive ticks. For the inner PID here, that error is a roll-rate error; its derivative is a roll-acceleration/reference-rate term. Setting PID Kd to zero still leaves roll-rate feedback through the inner PID’s P term.

LQR and PID can also work together

The teaching notebook 07 combines an LQR (or pole-placement) outer law with a steering-speed PI inner loop:

x → LQR → δ̇ref
espeed = δ̇ref − δ̇measured
S = clip(S + espeed × .02, −10, 10)
τsteer = clip(.01 espeed + .01 S, −5, 5)

Both loops run at 50 Hz. A separate rear-wheel P loop uses gain 0.1 and torque limit ±2 Nm. MuJoCo integrates at 0.5 ms; its XML takes two torque inputs. This PI closes steering-speed tracking, rather than replacing balance feedback with the three-stage PID above.

[14] notebook 07, cells 4, 6, 8

The backup is a third architecture

backup/source/new_balance/main_balance.py combines a nominal state-feedback outer loop with a manual steering-speed PD inner loop that sends C0:

Iq = clip(Kp(δ̇ref − δ̇meas)
  − Kd d(δ̇meas)/dt, limits)

Its D term acts on the measured steering rate, and the first derivative after reset is suppressed. That differs from the error-difference implementation in cascaded_main_balance.PID. The current source’s inner_pid.py is empty; it is not an active PID implementation.

Review scope: the project tree was inventoried and searched for control implementations; the balance controllers, imported nominal package, sensor/RC publishers, launch/configuration, relevant motor protocol, tuning tools, legacy paths and tutorial code were inspected. Peripheral servo and RC code was also read for integration context. Generated build/install/log trees, CAD, binary archives and unrelated bundled firmware/third-party stacks were not audited line by line. This is a source-grounded control explanation, not a claim of an exhaustive audit of every vendor file.

Model limits: small-angle, approximately fixed-speed nominal dynamics omit actuator lag, tire slip and full contact/multibody behavior. LQR’s unconstrained continuous-time optimality does not transfer automatically to sampled, delayed or saturated hardware. The PID gain heuristic does not establish closed-loop stability. The explorer shows only algebraic controller results and nominal instantaneous derivatives.
