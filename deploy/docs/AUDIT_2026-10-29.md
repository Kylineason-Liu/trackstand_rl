# Deployment audit — 2026-10-29

The default path remains **Trackstand-Balance-v1 / model_2500**, run
`2026-10-21_11-18-29`: 11 observations, bounded Beta means, MIT steering and
C0 rear torque. This audit fixes reproducible software faults; it does not
establish that any one fault caused a previously recorded balance failure.

## Scope and retained contract

Read the progress ledgers, active launch/configuration/package/model manifest,
all seven node entry points, shared contracts/protocols/telemetry, active vendor
serial parsing, servo transport and deployment tests. Compare observation/action
processing with current v1 training code and the recorded v1 alignment findings.
Experiment controllers and historical report snapshots are not deployment entry
points and were not rewritten.

- **Inputs:** corrected quaternion and bike-frame gyro; signed steering/rear
  A3 positions and A2 velocities. Rear displacement is rebased per episode, then
  adapted to the measured PhysX 4π branch. Steering keeps its fixed straight zero.
- **Policy:** checked self-contained ONNX, 11 inputs/two bounded actions, 50 Hz.
  Steering ×1.57, explicit position clipping, one 0.478-rad slew step per action.
  Rear ×6.28 Nm; no added software damping/friction compensation.
- **Motors:** targets held between policy updates; MIT steering/C0 rear and
  motor-control telemetry nominally 200 Hz. Feedback/state/status/fault division
  remains nominally 100 Hz. New AE queries share this scheduler.
- **Authority:** RC down disables balancing and requests stands down. Policy
  faults latch off; they do not automatically lower the stands. Ordinary motor
  recovery requires disabled output, confirmed disable, fresh feedback/status
  and steering within the existing five-degree threshold. Hard faults require restart.

Policy/model hashes, hardware IDs/signs, gear ratios, IMU mounting/bias values,
CRSF configuration, servo targets, limits, gains and frequency parameters are
preserved. No training/checkpoint, simulator or model-geometry change was made.

## Bugs fixed

| Area | Previous failure mode | Correction |
| --- | --- | --- |
| IMU partial freeze | Any checksum-valid packet refreshed one global timestamp. A frozen quaternion/gyro could look fresh while other packet types continued. | Separate valid raw/quaternion parse times, immutable tuples and a locked snapshot; neither unrelated packets nor one moving channel can keep the older time advancing. |
| IMU malformed payload | A checksum-valid short payload could raise during vendor decoding and kill the receive thread. | Adapter catches decoding errors without refreshing sample age or replacing its last valid snapshot; vendor files are preserved. |
| IMU ROS timestamp | Header represented publication time, concealing time since the channels were parsed. | Backdate the header to the older channel's host parse time. This does not identify UART wire arrival or onboard acquisition time. |
| Delayed ROS inputs | Policy callbacks replaced sample age with callback receipt time, including delayed valid messages. | Preserve IMU header age and motor-state publication age; reject stale/future timestamps. Motor-state field 4 retains its existing Unix publication-time meaning. |
| Hardware driver faults | MIT consumed AE reports but never requested them during runtime. Encoder/current replies alone do not supply the AE fault byte. | Request AE for **both** motors at startup and each nominal 100 Hz round. Missing/stale status gates enable; active loss latches off; reported driver faults remain hard faults. |
| Invalid motor commands | Malformed/nonfinite packets were ignored while the previous enabled target remained valid until timeout, even for a malformed disable. | All backends latch an invalid-command fault and invalidate command freshness. MIT also advances its withdrawal generation so an in-progress send guard rejects the old token. |
| Short motor-fault pulse | A True followed by False between 50 Hz policy ticks could be missed by the policy latch. | The callback immediately latches an active policy episode and publishes disable; a later False does not re-enable it. |
| RC down error path | RC down evaluated readiness unnecessarily; a motor-command publication exception could prevent publishing the stand-down request. | Bypass readiness for down; attempt stand-down publication in `finally`. This is not a guarantee of physical servo movement or delivery after ROS shutdown. |
| Diagnostic latency | Reliable observation/raw-action publication preceded the motor target. | Publish the motor target first. Cross-topic bag arrival order must not be used as an exact inference sequence identifier. |
| Servo error reports | Correct-checksum write/read responses with nonzero error bits were accepted as success/data. | Reject error acknowledgements/data, report enable failures, and still attempt the second stand after an OSError from the first. No automatic pose feedback/arming handshake is claimed. |
| Legacy feedback age | C0/C2 paired state was dated after the newer velocity query. Future pair timestamps could also pass publication checks. | Use the older position receipt time for pair freshness; reject future state timestamps in all backends. |
| Runtime legacy parameters | C0/C2 accepted parameter updates while retaining cached values, including `dry_run`. | Motor parameters are explicitly read-only after startup, like the MIT backend. CLI/YAML startup overrides still work. Restart after changing them. |
| Shutdown | Several entry points called `rclpy.shutdown()` after ROS signal handling had already shut down, or skipped shutdown after constructor/cleanup errors. | All seven entry points handle external shutdown and guarantee idempotent `try_shutdown()` in `finally`. Existing CAN/servo cleanup remains in their node destructors. |
| Validation/package | Nonfinite IMU configuration values were incompletely checked; quaternion norm could overflow; requirements omitted a transitive vendor dependency; package description still named v0. | Validate finite IMU/RC/servo-rate settings, use robust quaternion norm, include `smbus2`, and correct the package description to v1. |

## Interface and timing implications

No topic is renamed and no motor-command/state field is removed. Two fields are
appended to the MIT control array, preserving all prior indices:
`steering_driver_status_age_ms`, `drive_driver_status_age_ms`. The same fields
appear in motor-status JSON. Read the ordered field list in each array's label.

There are now **eight**, rather than six, serialized state queries per 100 Hz
round: A3/A2/A1/AE for each motor. Each has the existing 2 ms deadline. A worst-case
round can exceed 10 ms, so actual rates can fall below nominal; missed rounds do
not burst. The existing 50 ms feedback timeout also bounds driver-status age.
Check these ages and control timing on the Pi while recording a bag. A nominal
100 Hz software topic is not proof of 100 Hz fresh hardware responses.
The local [CAN protocol's AE section](../../tsinghua_bike_project/can_protocol.txt)
documents unsolicited fault reports every 200 ms, excluding communication faults.
The new queries reduce reliance on that unsolicited reporting; the old backend
could already detect a fault report when one arrived.

IMU age includes known host parse/publication/delivery delay, but not unknown
onboard fusion delay or UART buffering. Motor-state age still begins at its
publication; the motor backend separately bounds encoder-pair age. These remain
asynchronous measurements, not simultaneous hardware acquisition.

## Remaining boundaries before unsupported deployment

1. **Steering MIT total-torque protection remains unverified.** The simulator's
   ±5.6 Nm post-PD clamp is not established by F0's MIT encoding range or B3's
   position/speed-mode current limit. This audit does not invent a firmware cap
   or change the experimentally verified MIT gains.
2. **Motor-side deadman behavior remains unverified and unconfigured by this
   deployment.** Host freshness/disable logic cannot act during a complete process
   freeze or broken CAN connection. The local CAN protocol's CD section documents
   a volatile communication watchdog, disabled by default; the bike's live setting,
   which traffic refreshes it and MIT-mode behavior need supported hardware
   confirmation. No CD settings were changed by this software audit.
3. **Actuator/observation fidelity is not certified.** The measured rear replay
   discrepancy, actual firmware response, IMU fusion mode/latency and precise
   loaded plant dynamics remain separate hardware identification work. Existing
   steering replay success does not establish that this closed loop will balance.
4. **Legacy alternatives retain weaker protections than the default MIT node.**
   C0/C2 inherit the invalid-command/parameter/age/shutdown fixes, but are not
   upgraded to MIT's single CAN owner, AE freshness gate, kernel timestamping or
   acknowledged-disable state machine. Do not run multiple motor backends.
